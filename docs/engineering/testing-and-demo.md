# 검증 방법과 5분 시연

이 문서는 확인할 시나리오와 검증 범위를 설명한다. 현재 실행하지 않은 테스트를 통과한 것으로 표시하지 않는다. 날짜별 실제 결과는 인수인계에 남기고 이 문서에는 고정된 테스트 개수나 성능 수치를 복제하지 않는다.

## 검증 범위 구분

| 검사                           | 무엇을 확인하는가                                          | 이것만으로 주장할 수 없는 것                       |
| ------------------------------ | ---------------------------------------------------------- | -------------------------------------------------- |
| Web 단위·컴포넌트 테스트       | URL 해석, 조회 상태, 조건 적용, 상호작용, 접근성 의미 구조 | 실제 브라우저 배치·API 서버·DB 정합성 전체         |
| API HTTP 테스트                | Nest Controller·권한·입력·서비스 경로                      | 대체 Prisma 사용 시 실제 PostgreSQL 락·제약·동시성 |
| DB 연결·migration 확인         | 대상 DB와 schema 준비 상태                                 | 모든 업무 상태 전이의 정확성                       |
| 실제 브라우저 검사             | 화면 이동·키보드·모바일·요청 횟수·대기·복구                | 생산 운영 성과, 모든 사용자 환경                   |
| lint·typecheck·build·문서 검사 | 정적 규칙·타입·번들·참조 링크                              | 제품 사용성·운영 보안 인증                         |

[인증 HTTP 테스트](../../apps/api/test/auth.e2e-spec.ts)와 [예약 HTTP 테스트](../../apps/api/test/material-reservations.e2e-spec.ts)에는 대체 Prisma 구현이 있다. 테스트 파일 이름이 e2e라고 해서 실제 DB까지 검증했다고 설명하지 않는다.

## 명령과 준비

```bash
corepack pnpm lint
corepack pnpm --filter @sensor-mes/web test --maxWorkers=2
corepack pnpm --filter @sensor-mes/web build
corepack pnpm docs:check
```

전체 검사는 루트 package.json의 check와 test를 따른다. DB가 필요한 작업은 검증용 환경을 먼저 준비한다. 공유 DB를 재시드하거나 사용자 기록을 변경하는 시연은 별도 합의 없이 실행하지 않는다.

## 생산 흐름 DB 회귀 검증

[생산 흐름 테스트](../../apps/api/test/production-flow.postgres.spec.ts)는 세 제품의 초안 생성부터 발행, BOM 자재 예약·소비, 공정 완료, 검사 판정, 작업지시 완료까지 실제 PostgreSQL에서 검증한다. 소요량 초과 예약과 실적 합계 불일치도 검사한다. 테스트마다 하나의 트랜잭션을 사용하고 모든 생성 기록·재고 변경을 롤백한다.

시드가 준비된 로컬 DB의 연결 정보를 `apps/api/.env`에 설정한 뒤 저장소 루트에서 실행한다.

```bash
corepack pnpm test:postgres
```

기본 test에서는 DB 통합 검사를 건너뛰며 CI는 migration·seed 이후 test:postgres를 별도 필수 단계로 실행한다. [보류 검토 DB 테스트](../../apps/api/test/inspection-review.postgres.spec.ts)는 두 검토 요청 중 하나만 커밋되는지, 감사 저장 실패 시 현재 판정·검토 이력·후속 공정이 함께 롤백되는지 확인한다. 이 테스트는 전용 임시 작업을 생성하고 해당 ID의 기록만 정리한다. 전체 명령의 운영 부하 성능은 검증하지 않았다. 별도의 [상태 전이 테스트](../../apps/api/test/production-flow.spec.ts)는 검사 합격 후 차단 해제, 다른 차단 사유 보존, LOT별 수량, 최종 검사 대기를 확인한다.

## 처음 보는 사람을 위한 읽기 시연

1. 로그인에서 **데모 둘러보기**로 최고관리자 계정에 접속한다. 대시보드로 바로 진입한다. 아래 네 가지 담당자 계정도 업무 설명·시작 화면과 함께 항상 표시되며, 선택하면 해당 역할의 업무 화면으로 바로 진입한다.
2. 대시보드의 **처음 살펴볼 작업 → 작업 확인**을 누른다. 현재 보류 검사로 차단된 대표 작업을 먼저 보여 주고, 보류가 해소되었으면 검토 후 완료 사례로 연결한다. 해당 기록이 없으면 링크를 만들지 않는다.
3. 작업지시의 차단 사유와 공정 흐름을 확인하고, **검사**에서 보류된 검사 번호를 누른다.
4. 검사 상세의 최초 판정 사유·담당자·시간을 읽는다. 조회 시연에서는 판정·검토 확정 버튼을 누르지 않는다.
5. 작업지시 목록에서 메모가 **보류 검토 후 완료**인 사례를 열어 최초 보류와 검토 후 합격 이력을 비교한다. LOT 계보·감사이력은 같은 작업 번호를 기준으로 연결한다.
6. 개발 문서에서 화면의 조회 상태, API 권한, DB 트랜잭션과 검증 한계를 설명한다.

대표 사례가 필요하면 시드 준비 후 `corepack pnpm --filter @sensor-mes/api db:demo`를 실행한다. 네 사례는 생성·발행·예약·공정 시작·완료·검사 명령으로 만들어지며, 재실행은 기존 사례와 사용자 변경을 유지한다.
시간보다 이해가 우선이다. 데이터가 없거나 현재 역할로 연결할 수 없는 단계는 그 사실을 말하고 건너뛴다. 정상 완료를 연출하려고 데이터를 수정하지 않는다.

## 반드시 함께 볼 실패·대기 상태

- 세션 확인 전: 보호 데이터를 노출하지 않고 초기 준비 화면을 보여 준다.
- 첫 데이터 조회·문서 로딩: 실제 기다리는 영역에 스켈레톤을 표시한다. 보여주기용 지연을 추가하지 않는다.
- 같은 조건 재조회·페이지 변경: 이전 성공 내용과 배치를 유지하고 갱신 상태를 알린다.
- 실패·빈 결과: 원인에 맞는 다시 시도·조건 초기화·허용 화면 복귀가 있다.
- 권한 없음: 일반 역할의 직접 URL·명령 접근을 거부한다. 최고관리자의 전체 권한도 API 공통 guard를 통과하며, CSRF·Origin·만료·수량·상태 검증과 마지막 관리자 보호가 유지되는지 확인한다.
- 네트워크: 실제 /api 요청만 세고 메뉴 hover, 최초 진입, 상세, 재조회와 테마를 나눠 측정한다.
- 작은 화면·다크·키보드: 페이지 가로 넘침, 초점, 표 내부 스크롤, 최소 14px를 확인한다.

## 포트폴리오 설명의 순서

문제 → 대안과 선택 이유 → 실제 코드 → 성공·실패 검증 → 남은 한계 순으로 설명한다. 테스트 개수나 문서 개수만으로 완성도를 주장하지 않는다. 실제 제조 현장 운영, 고객, 성능 개선 수치, 본인 기여 범위는 확인된 사실만 적는다.
