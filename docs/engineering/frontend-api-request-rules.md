# 프런트엔드 API 요청 규칙

## 조회 요청의 소유자

페이지·기능이 조회 필요 시점을 정하고, entities의 조회 함수와 shared/api를 통해 요청한다.
동일 화면의 제목·본문은 이미 받은 데이터를 함께 사용한다. 경로 제목만 만들기 위한 별도 GET을 추가하지 않는다.

## 중복과 재조회 구분

- 진행 중인 동일 GET은 한 요청을 공유한다. URL과 헤더가 같을 때만 공유하고 서로 다른 필터·페이지·표시 건수·헤더는 합치지 않는다.
- 완료 응답이나 오류를 캐시에 남기지 않는다. 사용자가 조회·새로고침을 누르면 최신 데이터를 다시 요청한다.
- POST·PATCH·PUT·DELETE 등 업무 명령은 합치거나 자동 재시도하지 않는다.
- 메뉴 hover/focus만으로 보호 경로를 미리 읽지 않는다. 실제 이동에서 세션과 권한을 확인한다.
- 실제 경로·조회조건 이동의 세션 GET과 업무 GET은 서로 다른 목적의 정상 요청이다. 숫자를 줄이기 위해 권한 확인을 생략하지 않는다.

## 최초 문서의 인증 요청

- 보호 경로의 HTML은 앱 코드·스타일을 받는 동안 실제 `/api/auth/me` GET을 먼저 시작한다. 공개·로그인 경로에는 별도 선행 요청을 추가하지 않는다.
- 이 문서의 원래 응답 Promise만 메모리에서 한 번 인계한다. 이전 문서·세션 저장값을 재사용하는 캐시가 아니다. 앱이 시작되기 전에 응답이 도착했더라도 동일 요청을 이어서 파싱·검증한다.
- URL·GET·기본 Accept 헤더와 요청 옵션이 동등한 경우만 인계한다. 사용자 지정 헤더·옵션은 별도 요청이며 초기 요청이 취소됐거나 소비 시 30초를 넘겼으면 최신 인증을 다시 요청한다.
- 선행 요청은 `credentials: same-origin`, `cache: no-store`를 사용한다. 완료 뒤 추가 조회는 항상 새 요청이다. 초기 응답을 브라우저 저장소에 보관하지 않는다.
- 로그인·로그아웃은 미소비 선행 요청과 진행 중 읽기를 모두 취소한다. 소비 중 취소·응답 본문 파싱 중 인증 변경도 기존 취소 규칙을 따르며 401·네트워크 오류·잘못된 세션 응답을 성공으로 처리하지 않는다.

## 공개 로그인 화면의 세션 확인

- /login은 공개 화면부터 렌더링하고 현재 세션을 뒤에서 확인한다. 확인 때문에 별도 전면 제목이나 로딩 화면을 표시하지 않는다.
- 유효한 서버 응답일 때만 업무 첫 경로로 이동한다. reason=role-changed 등의 URL 값으로 인증을 건너뛰거나 로그아웃 성공을 추정하지 않는다.
- 사용자가 역할을 선택하면 이전 확인 요청을 취소한다. 화면 이탈 후나 취소 후의 늦은 응답은 새 로그인·이동을 덮어쓰지 못한다.
- 미인증·통신 오류에도 로그인 화면은 유지한다. 실제 로그인 실패는 선택한 로그인 요청의 오류로 알리고 보호 라우트의 인증 검증은 그대로 수행한다.

## 취소·변경·역할 경계

- 한 화면이 떠나도 같은 GET을 기다리는 다른 화면의 요청은 취소하지 않는다.
- 기다리는 곳이 모두 사라지면 요청을 취소한다. 개발 모드의 cleanup/setup은 같은 실행 구간 안에서 요청 소유권을 이어받는다.
- 이전 조회가 늦게 끝나도 최신 조건의 결과를 덮지 못하게 한다.
- 업무 명령 전후에는 진행 중 읽기 요청의 공유 인덱스를 비워 변경 전 읽기에 새 조회가 합류하지 않게 한다.
- 로그인·로그아웃 시 진행 중 읽기를 취소하고 공유 상태를 비운다. 사용자·역할이 바뀐 뒤 이전 읽기를 재사용하지 않는다.
- 세션·권한의 완료 응답을 장기 캐시하거나 브라우저 저장소에 별도 복제하지 않는다. API의 권한 검증을 유지한다.

## 정적 가이드 예외

가이드 원문은 API 응답이 아니라 빌드에 포함된 공개 Markdown이다. 완료 원문과 진행 중 import를 현재 문서의 메모리에만 재사용한다. 재진입 시 완료 원문을 첫 렌더부터 사용하며 오류는 보관하지 않는다. 새로고침은 새로운 문서이므로 필요한 모듈과 세션을 다시 준비할 수 있다. 업무 결과·세션·권한의 캐시 금지와 혼동하지 않는다.

## 사용자 권한 변경

PATCH /api/admin/users/:id/access는 기존 역할 코드·활성 여부·사유·목록에서 읽은 updatedAt을 보낸다. 확인 단계 이후 한 번만 요청하고 변경 뒤 목록을 재조회한다. 409·불명확한 통신 결과를 자동 재시도하지 않는다. 서버는 마지막 활성 관리자 보호, 대상의 전체 세션 폐기, 권한 변경과 감사 기록의 원자성을 보장하는 트랜잭션을 사용한다. 실제 DB 경쟁 검증은 별도 환경에서 수행한다.

## 화면 안정성과 검증

- 목록은 최초 조회·빈 결과·오류에도 같은 표·머리글·페이지네이션을 유지한다. 첫 조회는 빈 행 영역에 로딩을 표시하고, 재조회는 이전 행을 유지하면서 행 내부 조작을 막고 갱신 상태를 알린다.
- 메뉴 이동의 인증·코드 로딩을 기다리는 동안 기존 화면과 별도 진행 표시를 유지한다. 인증 확인이 끝나기 전 새 화면을 표시하지 않으며, 세션 만료는 기존 로그인 이동 규칙을 따른다.
- 개발 StrictMode는 유지한다. 중복을 숨기기 위해 개발 검사를 끄지 않는다.
- 네트워크 검사는 실제 /api 경로의 요청만 센다. Vite의 src/.../api/... 모듈 다운로드는 업무 API 호출이 아니다.
- 최초 진입, 메뉴 hover와 클릭, 상세, 페이지 이동, 표시 건수 변경, 같은 조건 재조회, 테마 변경을 각각 측정한다.
- 단위 검사는 공유, 한 소비자 취소, 전체 취소, StrictMode 전환, 오류 후 재조회, 서로 다른 요청, 명령·인증 경계를 포함한다. 문서 선행 요청의 단일 인계·중복 없음·만료·취소·미처리 오류 방지와 실제 세션 응답 검증도 포함한다.
