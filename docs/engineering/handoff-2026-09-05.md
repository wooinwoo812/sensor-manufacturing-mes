## 3. 왜 그렇게 했는가 (근거 위치)

- 디자인 결정 표(이전 / 이후 / 이유): [frontend-design-system.md](frontend-design-system.md)
  2.7 절. 간격 소유 규칙: 2.8 절. 검증 이력: 8.11 절.
- 코드 구조 결정: [frontend-architecture.md](frontend-architecture.md) 8.2.1 절
  (`useLoadState`).
- 토큰 값의 이유: `apps/web/src/app/styles/tokens.css` 주석.
- 공용 컴포넌트의 규칙: 각 파일 상단 JSDoc (`Panel`, `KeyValue`, `DataTable`,
  `FilterBar`, `PageHeading`, `Pagination`, `Badge`, `TableSkeleton`, `PageCrumb`).
- 커밋 메시지 본문에도 같은 이유를 한국어로 적었다.

새 화면을 만들 때 지켜야 하는 규칙은 2.8 절과 8.2.1 절 두 곳만 읽으면 된다.

## 4. 어떻게 확인하는가

```bash
corepack pnpm check        # lint(0 경고) → typecheck → test(web 93, api 131) → build → docs:check
corepack pnpm dev          # http://localhost:5173 (API 3000)
```

화면 확인은 로그인 화면의 역할 버튼 5개로 한다. 비밀번호는 전 역할 동일
(`SensorDemo!2026`). 데모 데이터는 `corepack pnpm db:seed` 로 언제든 되돌린다
(발행·시작·판정을 눌러 본 뒤에는 재시드).

## 6. 감시자(리뷰어) 체크리스트

이후 작업은 다른 사람이 하고, 리뷰어는 아래만 본다.

- 페이지 코드에 `mt-*`, `space-y-*`, 임의 padding 이 새로 들어왔는가 → 공용 컴포넌트로 옮긴다
- 조회 로직에 자체 `useEffect` 가 생겼는가 → `useLoadState` 를 쓴다
- 서버 코드(`MATERIAL_SHORTAGE` 같은 enum)가 화면에 그대로 보이는가 → entities 의 라벨 맵
- 새 상세 화면에 `PageCrumb`, `PageHeading.back`, `eyebrow` 가 있는가
- 배지가 두 줄로 꺾이거나 표가 1440px 에서 가로 스크롤을 만드는가
- 다크 모드에서 라이트와 같은 구조로 보이는가
- `corepack pnpm check` 가 경고 0 으로 통과하는가
- 디자인 결정을 바꿨으면 2.7 절 표에 한 줄(이유 포함)을 추가했는가
